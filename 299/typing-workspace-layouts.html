Typing workspace: five layouts

Mockups for Jdreioe/Wingmate#299, second round. Each layout is built around one Communicator situation and access method: touch typing, dwell and tremor, tablets, conversation, and switch or eye gaze. They share one Message bar, and a Typing Screen made from the Page elements Wingmate already has (Page navigation, Phrase collection, Action strips), so most of them could ship as a Typing Screen template rather than new screen code.

0 Today on Android

For reference, drawn in the same style. Since ab075ee1, Android renders the old PhraseGrid again instead of the Typing Screen tray from #248 (TypingScreenTray and CompactPhraseRow still exist but nothing calls them).

1 Composer with an input tray

A messaging-app composer, as sketched in #248. The Message bar sits directly above whichever input surface is open. + swaps the keyboard for the Typing Screen; the same button then shows a keyboard icon and swaps back. While typing, a compact Phrase row keeps the active Page's Phrases one tap away.

  1. 1+ / keyboard is the only switch between keyboard and Typing Screen. Tapping the Message field also brings the keyboard back.
  2. 2Compact Phrase row of the active Page while the keyboard is open, so Phrases stay reachable while typing.
  3. 3Held message is shown in the open with a labelled Swap, instead of as a bookmark icon whose state you have to remember.
  4. 4Speak lives in the Message bar, the largest round target, on the thumb side.
  5. 5Two Action strips: SSML, then speech controls with text labels. Secondary language is a labelled EN button plus an underline and badge in the text.

Who it's for

  • Touch typists who mix free text and Phrases in one Message.

Cost

S–MMost of it already exists. Rewire TypingScreenTray and CompactPhraseRow into PhraseScreen, then polish. This fixes the regression, and I recommend it as the base for everything below.

2 Fixed targets for dwell and tremor

Same composer and tray, but nothing in the Typing Screen scrolls or moves. Phrases are paged with large Previous/Next buttons, and the speech controls sit in a fixed column on the right, so every target stays in the same place from one use to the next. That muscle memory matters for pointer, dwell and head-tracking users.

  1. 1Dwell progress uses the existing dwell/hold activation: an outline marks the target and a bar fills inside it, so progress doesn't depend on color alone.
  2. 2Fixed control column: Speak is the tallest target. Stop, Delete and Hold never change position. Disabled commands stay visible.
  3. 3Paging instead of scrolling: a 2×3 Phrase grid with large Previous/Next buttons, because scroll gestures are hard with dwell, tremor or a head pointer.
  4. 4Rest mode is always one target away, since it's what stops accidental selections while resting.

Who it's for

  • Communicators with tremor or reduced motor control, and dwell, head-pointer or OS eye-tracking users on a phone.

Cost

MNeeds one new Phrase collection presentation ("paged", next to compact and expanded) and a vertical Action strip. Everything else is template layout.

3 Side by side on tablets and landscape

On a wide screen there's no reason to make the keyboard and the Typing Screen take turns. The Message bar and keyboard stay on the left, and the Typing Screen stays open on the right. On a phone this falls back to layout 1.

  1. 1Both input surfaces at once on wide screens. Taking turns only exists to save space on phones.
  2. 2Partner display (the existing fullscreen / external display) gets a visible button, because tablets are often shown to the conversation partner.
  3. 3One combined Action strip: SSML on the left, speech controls on the right, all inside the Typing Screen.

Who it's for

  • Tablet users and wheelchair-mounted devices; the Pixel landscape work in #291.

Cost

SBreakpoint logic in PhraseScreen on top of layout 1.

4 Conversation above the composer

The empty space above the Message bar shows what the Communicator has just said, like a chat thread. "Can you say that again?" is one of the most common requests in AAC conversations, and here the answer is one tap on the replay button. It uses the existing private History and is off when History is off.

  1. 1Replay is a separate 44dp button. Tapping the bubble loads it into the Message. Two targets, two clear results, no long-press needed.
  2. 2The thread shows only what Wingmate spoke, so nothing from the partner is ever captured. The dashed note is a hint, not a recording.
  3. 3Held message sits between the thread and the composer: visibly "set aside, not said yet".

Who it's for

  • Everyday back-and-forth conversation, especially in noisy places where the partner often asks for a repeat.

Watch out

  • History is private. The thread needs a quick "hide" option for when someone is looking over the Communicator's shoulder, and must respect the existing History-visibility setting.

Cost

MRead-only view over SaidTextRepository, replay through the existing speak path. No new data.

5 Whole-screen grid for switch scanning and eye gaze

For switch and eye-gaze users, even the Message bar and the controls become large cells in one Grid, which the scanner walks row by row. No system keyboard, no scrolling, no small chips. The Typing Screen is already a Screen, so this is a template of the same Page elements with larger cells and a scan order, not a separate app.

  1. 1Row-then-cell scanning with a thick outline, which reads on any background. Switch scanning on Android is still open in #226; this is the layout it would drive.
  2. 2Speak is the first cell in scan order after the Message, so finishing a Message is the shortest scan path.
  3. 3Pages, spelling (ABC), Hold and Rest are cells in one row, not small chips. ABC opens a scannable letter Page instead of the system keyboard.
  4. 4Previous/Next are cells in a fixed corner, so they're reachable by scanning, dwell or a mapped key (#111).

Who it's for

  • Switch users, eye-gaze users (TD-I13, #129; webcam, #276), and anyone who can't use the system keyboard.

Cost

LThe layout is a template. The real work is Android switch scanning (#226), a letter Page for ABC, and a Message bar that works as a Page element.
